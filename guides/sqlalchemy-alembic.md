## 1. Core Philosophies: ORM-2.0

SQLAlchemy/Alembic-specific principles only. TDD, security, SQL design, and the Python language come from §0.

- **2.0 style is the only style.** Typed `Mapped[]` / `mapped_column()` models on a `DeclarativeBase`; queries via `select()` + `Session.execute()`. The 1.x `Column()`-without-annotation models and the `Session.query()` Query API are **legacy** — flag and reject them in new code.
- **Core vs ORM is a deliberate choice.** ORM for domain objects and unit-of-work; Core (`select()`/`insert()` against `Table`/`text()`) for bulk ETL and performance-critical paths. Both share the same `select()` construct in 2.0.
- **Loading is explicit.** Every relationship declares its strategy; the N+1 problem is designed out, not discovered in production.
- **The session is a unit of work** with explicit transaction boundaries — context-managed, never autocommit, never shared across threads/tasks.
- **Migrations are reversible and reviewed.** Autogenerate is a draft, not an answer; every migration has a tested `downgrade()`.

**Verified Code**: Agent-generated code MUST pass every gate in §2 before delivery.

## 2. Requirements (MANDATORY, auditable)

RFC-2119 keywords. IDs `SA-<TOPIC>-<NN>`. Each row has a binary gate; rows binding a shared rule cite its owner.

| ID | Requirement | Verify | Gate |
|----|-------------|--------|------|
| SA-ORM-01 | Models MUST use 2.0 typed style: `DeclarativeBase` + `Mapped[]` + `mapped_column()`. No bare `Column()` attributes | `grep -rEn '= Column\(' src/` ; review | no matches |
| SA-ORM-02 | Queries MUST use `select()` + `Session.execute()`. No `Session.query()` / `.filter()` Query API in new code | `grep -rEn '\.query\(' src/` | no matches |
| SA-LOAD-01 | Every `relationship()` MUST set an explicit loading strategy; N+1 patterns MUST be eager-loaded | review ; SQL-count test | no implicit lazy in hot paths |
| SA-SES-01 | Sessions MUST be context-managed with explicit commit/rollback; `autocommit` MUST NOT be used | `grep -rEn 'autocommit' src/` ; review | no autocommit |
| SA-ASY-01 | Async sessions MUST set `expire_on_commit=False`; no implicit IO-on-attribute-access | review | exit 0 |
| SA-POOL-01 | Engine MUST configure pooling (`pool_pre_ping=True`, sized `pool_recycle`) | review engine config | configured |
| SA-MIG-01 | Every migration MUST pass the upgrade→downgrade→upgrade cycle on a populated DB | `pytest tests/test_migrations.py` | exit 0 |
| SA-MIG-02 | Autogenerated migrations MUST be hand-reviewed before commit (autogenerate misses renames/types) | PR review ; `alembic check` | reviewed, no drift |
| SA-MIG-03 | `downgrade()` MUST be implemented (no bare `pass` without `# DOWNGRADE_NOT_NEEDED:`) | `pytest` AST check (§7) | exit 0 |
| SA-MIG-04 | Migration history MUST have a single head | `alembic heads` | one head |
| SA-SEC-01 | All values MUST be bound parameters; no string interpolation into SQL (see `secure-coding.md`) | `grep -rEn 'text\(.*%|text\(f' src/` | no matches |
| SA-ERR-01 | `IntegrityError`/`StaleDataError` MUST be handled at a defined boundary (see `error-handling.md`) | review | handled |
| SA-TST-01 | Models, constraints, and loading MUST be test-first (see `tdd.md`); test on SQLite + the prod dialect | `uv run pytest` | exit 0, 0 skips |

> **Forbidden**: 1.x `Column()`/`Query()` in new code; sessions without a context manager; `expire_on_commit=True` under asyncio; presenting a migration whose downgrade was never executed; trusting autogenerate output unreviewed; interpolating values into `text()`.

## 5. SQLAlchemy 2.0 Specifics

The unique value of this guide. All examples are 2.0-only.

### A. Declarative base, naming convention, mixins

The naming convention is **required** so Alembic autogenerate produces stable, deterministic constraint names (without it, dropping a constraint in a migration fails because the DB's auto-name is unknown).

```python
from datetime import datetime
from sqlalchemy import MetaData, func
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

NAMING = {
    "ix": "ix_%(column_0_label)s", "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}

class Base(DeclarativeBase):
    metadata = MetaData(naming_convention=NAMING)

class TimestampMixin:
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())
    updated_at: Mapped[datetime] = mapped_column(server_default=func.now(), onupdate=func.now())
```

### B. Typed models — `Mapped[]` drives the schema

The annotation is the source of truth: `Mapped[int]` → NOT NULL, `Mapped[str | None]` → nullable. Override specifics in `mapped_column()`.

```python
from enum import Enum
from sqlalchemy import String, Text, CheckConstraint, Index
from sqlalchemy.orm import relationship

class UserStatus(str, Enum):
    PENDING = "pending"; ACTIVE = "active"; SUSPENDED = "suspended"

class User(Base, TimestampMixin):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(String(255), unique=True, index=True)  # NOT NULL via Mapped[str]
    bio: Mapped[str | None] = mapped_column(Text)                              # nullable via | None
    status: Mapped[UserStatus] = mapped_column(default=UserStatus.PENDING)     # native Enum mapping

    addresses: Mapped[list["Address"]] = relationship(
        back_populates="user", cascade="all, delete-orphan", lazy="selectin",
    )
    __table_args__ = (Index("ix_users_status_created", "status", "created_at"),)
```

Use `from __future__ import annotations` (or string forward refs) plus `TYPE_CHECKING` imports for cross-module relationships to avoid circular imports.

### C. Relationships & loading strategies — the N+1 problem

This is the highest-value decision in the ORM. Pick the strategy at the call site with `.options()`, or set a sensible default on the `relationship()`:

| Strategy | Mechanism | Use when | N+1 risk |
|---|---|---|---|
| `selectin` | one extra `IN (...)` query per collection | **default for collections** (one-to-many, many-to-many) | none |
| `joined` | single `LEFT OUTER JOIN` | many-to-one / one-to-one scalars | none (but row fan-out on collections — avoid) |
| `lazy` (`select`) | query on first access | rarely-touched relations in sync code only | **high** — emits a query per parent |
| `raise` | raises on access | enforce "must be eager-loaded" in async/hot paths | n/a (fails loud) |
| `subquery` | correlated subquery | legacy; prefer `selectin` | none |

```python
from sqlalchemy import select
from sqlalchemy.orm import selectinload, joinedload

# collection → selectinload (2 queries total, no fan-out)
stmt = select(User).options(selectinload(User.addresses)).where(User.status == UserStatus.ACTIVE)
# scalar (many-to-one) → joinedload (1 query)
stmt = select(Address).options(joinedload(Address.user))
```

Footgun: `lazy="select"` inside a loop over parents is the classic N+1 — `for u in users: u.addresses` fires one query per user. In **async** code, lazy access raises `MissingGreenlet`; set `lazy="raise"` or `lazy="selectin"` and always eager-load. Verify with a query-count assertion (see §7) — owned SQL-design rationale lives in `sql.md`.

### D. Querying — `select()` + `execute()` (Core/ORM unified)

```python
from sqlalchemy import select, func, update

# scalar / one-or-none
user = session.execute(select(User).where(User.id == uid)).scalar_one_or_none()
# list of ORM objects
rows = session.execute(select(User).order_by(User.created_at.desc())).scalars().all()
# aggregate + pagination
total = session.execute(select(func.count()).select_from(User.__table__)).scalar_one()
page = session.execute(select(User).limit(20).offset(40)).scalars().all()
# bulk UPDATE (no Python round-trip)
session.execute(update(User).where(User.id.in_(ids)).values(status=UserStatus.ACTIVE))
```

`.scalars()` unwraps the single-entity rows; without it you get `Row` tuples. Prefer keyset (`WHERE id > :last`) over large `OFFSET` for deep pagination — rationale in `sql.md` / `performance.md`.

### E. Session lifecycle & transactions (sync)

The session is the **unit of work**: it tracks new/dirty/deleted objects and flushes them as one transaction. One session per request/task; never share across threads.

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

engine = create_engine(settings.database_url, pool_size=10, max_overflow=20,
                       pool_timeout=30, pool_recycle=1800, pool_pre_ping=True)
SessionLocal = sessionmaker(engine, expire_on_commit=False)

def create_user(email: str) -> int:
    with SessionLocal() as session, session.begin():   # begin() = commit on success, rollback on raise
        user = User(email=email)
        session.add(user)
        session.flush()        # assign PK without ending the transaction
        return user.id
```

`session.begin()` gives an explicit transaction boundary; the outer `with` closes the session. Never call `commit()` without surrounding error handling (see `error-handling.md`).

### F. Async (`AsyncSession`)

Use `create_async_engine` with an async driver (`postgresql+asyncpg`, `mysql+asyncmy`, `sqlite+aiosqlite`). The API mirrors sync but every IO call is awaited.

```python
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker, AsyncSession

engine = create_async_engine(settings.async_dsn, pool_pre_ping=True, pool_recycle=1800)
AsyncSessionLocal = async_sessionmaker(engine, expire_on_commit=False)  # MUST be False (SA-ASY-01)

async def get_active(uid: int) -> User | None:
    async with AsyncSessionLocal() as session:
        # eager-load: lazy access would raise MissingGreenlet outside the await chain
        stmt = select(User).options(selectinload(User.addresses)).where(User.id == uid)
        return (await session.execute(stmt)).scalar_one_or_none()
```

`expire_on_commit=False` is mandatory: with it `True`, attribute access after commit triggers a lazy reload — impossible to await transparently. For FastAPI, yield the session from a dependency. Use `pool_recycle` shorter than the DB's idle timeout.

### G. Constraints, indexes, and IntegrityError

Declare uniqueness/checks/FKs in the model (`__table_args__`, `ForeignKey(..., ondelete="CASCADE")`); the DB enforces them. Catching the violation is an error-handling concern:

```python
from sqlalchemy.exc import IntegrityError
try:
    with SessionLocal.begin() as s: s.add(User(email=dup))
except IntegrityError as e:        # strategy/boundary owned by error-handling.md
    raise EmailTakenError(dup) from e
```

### H. Security binding

Parameterization is **automatic** in the ORM and Core — `where(User.email == val)` and `text("... WHERE x = :v")` bind `val`/`:v` safely. The only way to reintroduce injection is f-strings/`%`/`.format()` into `text()` — forbidden (SA-SEC-01). Load the DSN from config (`env-config.md`); grant the runtime DB user least privilege and use a separate higher-privilege user for migrations (policy: `secure-coding.md`, dialect: `postgresql.md`/`mysql-mariadb.md`).

## 6. Alembic Migrations

The unique value on the schema-evolution side.

### A. `env.py` and autogenerate

`target_metadata = Base.metadata`. Enable `compare_type=True` and `compare_server_default=True` so column-type and default changes are detected:

```python
context.configure(connection=connection, target_metadata=Base.metadata,
                  compare_type=True, compare_server_default=True)
```

```bash
alembic revision --autogenerate -m "add user preferences"   # generate DRAFT
alembic upgrade head            # apply
alembic downgrade -1            # roll back one
alembic check                   # CI: models vs DB drift (SA-MIG-02)
alembic history --verbose       # audit
alembic upgrade head --sql      # offline SQL for DBA review
```

### B. Autogenerate limits — ALWAYS hand-review (SA-MIG-02)

Autogenerate **detects** added/removed tables & columns, index/unique/FK changes, nullable changes, and (with the flags above) type/server-default changes. It **misses or mis-renders**:

- **Renames** — sees a `DROP` + `ADD` (data loss). Rewrite by hand to `op.alter_column(..., new_column_name=...)`.
- **`CHECK` constraints**, some default changes, and most things on **SQLite** (limited reflection).
- **Table/column-level data migrations** — never generated; you write the `op.execute(...)` / batched DML.
- Server defaults expressed differently than the DB stores them → spurious diffs.

Review every generated `upgrade()` and `downgrade()` before committing.

### C. Reversible migrations & data migrations

Every migration has a working `downgrade()` (SA-MIG-03). Add columns safely (nullable, or with a `server_default` so existing rows backfill without a table rewrite — PG 11+), then tighten:

```python
def upgrade() -> None:
    op.add_column("users", sa.Column("status", sa.String(20),
                  nullable=False, server_default="active"))   # existing rows get a value
    # data migration: batch large backfills to avoid long locks
    op.execute("UPDATE users SET status = 'active' WHERE status IS NULL")

def downgrade() -> None:
    op.drop_column("users", "status")
```

For non-nullable adds on a populated table, use the three-phase pattern: add nullable → backfill in batches → `alter_column(nullable=False)`. Index creation that must not block writes uses the dialect's online form (`postgresql_concurrently=True`, outside a transaction) — engine specifics live in `postgresql.md`/`mysql-mariadb.md`.

### D. Branching & merge

Parallel development creates **multiple heads**; CI must fail on this (SA-MIG-04). Resolve with a merge revision:

```bash
alembic heads                       # detect divergence
alembic merge -m "merge heads" <rev1> <rev2>
```

Use `branch_labels`/`depends_on` only for genuinely independent migration trees (e.g. multi-tenant or plugin schemas).

### E. SQLite — batch (move-and-copy) mode

SQLite can't `ALTER`/`DROP` most columns or add constraints in place. Alembic's **batch mode** recreates the table, copies data, and swaps — required for any non-trivial SQLite change (and for CI that tests on SQLite):

```python
def upgrade() -> None:
    with op.batch_alter_table("users") as batch:
        batch.alter_column("first_name", existing_type=sa.String(50), type_=sa.String(100))
        batch.drop_column("legacy_field")
```

Set `render_as_batch=True` in `env.py` to make autogenerate emit batch ops when targeting SQLite. Reason about whether your prod dialect needs the same care — Postgres/MySQL usually don't.

## 7. Testing Migrations & Models

Test-first and coverage policy is owned by [`tdd.md`](guides://tdd.md); the runner is `uv run pytest` (see `python.md`). The SQLAlchemy/Alembic-specific bindings:

- Unit-test on `sqlite:///:memory:` (fast, isolated); **integration-test on the production dialect** (a Postgres/MySQL test container) — SQLite hides dialect bugs.
- Assert constraints by expecting `IntegrityError`; assert loading strategy by counting emitted SQL (catch N+1 regressions).
- **Every migration MUST pass upgrade → downgrade → upgrade on a populated DB** (SA-MIG-01), and have a non-empty `downgrade()` (SA-MIG-03).

```python
from alembic import command
from alembic.config import Config
from sqlalchemy import create_engine, text

def alembic_cfg(db_url: str) -> Config:
    cfg = Config("alembic.ini"); cfg.set_main_option("sqlalchemy.url", db_url); return cfg

def test_upgrade_downgrade_cycle(tmp_path):
    url = f"sqlite:///{tmp_path/'t.db'}"; cfg = alembic_cfg(url)
    command.upgrade(cfg, "head")
    with create_engine(url).begin() as c:
        c.execute(text("INSERT INTO users (email, status) VALUES ('a@b.c', 'active')"))
    command.downgrade(cfg, "-1")
    command.upgrade(cfg, "head")          # cycle MUST succeed and preserve rows

def test_all_downgrades_implemented():    # SA-MIG-03 guard
    import ast, pathlib
    for f in pathlib.Path("alembic/versions").glob("*.py"):
        tree = ast.parse(f.read_text())
        for n in ast.walk(tree):
            if isinstance(n, ast.FunctionDef) and n.name == "downgrade":
                bare = len(n.body) == 1 and isinstance(n.body[0], ast.Pass)
                assert not bare or "# DOWNGRADE_NOT_NEEDED:" in f.read_text(), f.name
```

In CI, run `alembic upgrade head` + `alembic downgrade base` + re-upgrade against a real Postgres service, then `alembic check` for drift (orchestration owned by `ci-cd.md`).

## 8. Observability & Pooling Quick Notes

Metrics/tracing policy is owned by [`observability.md`](guides://observability.md); performance by [`performance.md`](guides://performance.md). SQLAlchemy bindings:

- **Slow-query logging**: hook `before_cursor_execute`/`after_cursor_execute` engine events to time statements; emit a structured warning over a threshold. `echo=True` is for local debugging only — never production.
- **Pool sizing**: start at `pool_size ≈ 10`, `max_overflow ≈ 20` per app instance; `pool_pre_ping=True` to survive DB restarts; `pool_recycle` below the server's idle timeout. `QueuePool limit ... reached` means a connection leak (a session not closed) or undersized pool.
- **Optimistic locking**: `__mapper_args__ = {"version_id_col": version}` raises `StaleDataError` on concurrent update — handle per `error-handling.md`.
